# Design — WP-0.7 Data-model baseline

## 1. Scope
- In scope (IDs): none implemented. The WP documents the R1 schema that serves every R1 requirement with a data impact (210 R1 IDs, plus OUT-01/OUT-02 data basis per D-26). Nothing is migrated.
- Deliverables (phase-0-foundation.md, WP-0.7):
  1. `docs/02-architecture/erd/<module>.md` for each of the 11 modules: Mermaid `erDiagram`, columns with types per `data-model-conventions.md`, constraints and indexes, append-only tables.
  2. Personal-data registry, the design of `config/privacy.php` (D-14): `docs/02-architecture/erd/pii-registry.md`.
  3. Migration order by module dependency: `docs/02-architecture/erd/README.md` §Migration order.
  4. Mapping table: every table named in `spec/14` → approved name or reason for change: `erd/README.md` §Spec/14 mapping.
  5. Checklist generated by `spec-reader`: every R1 requirement with a data impact → the columns that serve it: `docs/02-architecture/erd/r1-coverage.md`. Raw extracts already in `specs/WP-0.7/inventory/` (9 files, one per spec group).
- Added to make the acceptance criteria mechanical (same approach as WP-0.3): `scripts/check-erd.php` + `scripts/test-erd.php` and a `verify.sh` gate (§5).
- Explicitly out of scope:
  - Writing migrations, models or `config/privacy.php` itself (WP-1.1 onward; `config/privacy.php` lands with WP-1.5).
  - Seeding settings values or adding settings keys the spec does not name. The `settings` table is key/value, so a missing key never changes the schema.
  - R2/R3 tables (`content_versions`, `qr_codes`, `tests`, `questions`, `test_attempts`, `test_answers`, `settlements`). The mapping table marks them `deferred-R2` with the requirement that brings them.
  - Business logic choices left to the owning WP (dunning schedule, refund eligibility, report sampling, compensation formulas). The schema stores their inputs and results only.
- Decisions applied (all Default unless noted):

| Decision | Shape in the schema |
| --- | --- |
| D-01 | One subscription per child: `subscriptions.student_id` + `family_id`. "Oldest active subscription is the first child" is a query over `subscriptions.started_at`. The discount applied is stored on `invoice_lines` (`discount_rule_id`, `discount_minor`). |
| D-02 | `compensation_lines` per executed session for `class_sessions.actual_teacher_id`, `kind = session`, amount in fils; `teacher.substitute_per_session_jod` is not read by the schema. |
| D-03 | `compensation_lines.paid_student_count` snapshot taken at session start; trial and paused enrollments excluded by query (`class_enrollments.kind`, `status`). |
| D-04 | `compensation_lines.period_month_on` (first day of month in `Asia/Amman`); `compensation_statements` unique `(teacher_id, period_month_on)`. |
| D-05 | `credit_lots`: `subscription_id`, `payment_allocation_id`, `cycle_no`, `pool`, `qty_granted`, `amount_paid_minor` + `currency`, `effective_at`, `cycle_end_at`, `base_expires_at`, `expires_at` (cache). Derived: rebuildable from the purchase entry, its payment allocation, the rule version and append-only `credit_lot_extensions` (freezes); the lot is inserted first and every paid-pool entry carries `lot_id` (ADR-007 §5 note), so there is no FK cycle. |

Reads beyond the WP's "اقرأ فقط" row (recorded in notes.md): `architecture.md` §3 (which module owns which table; ADR-001 points to it) and constitution Art. 5 §2 (exact wording of the ledger unique key).

## 2. Traceability
No requirement ID is implemented, so no test is named after one. Each R1 ID gets exactly one row in `erd/r1-coverage.md` (`Y` with `table.column` references, or `N` with a reason), and the checker enforces it. The checker gets a fixture-based self-test like `scripts/test-traceability.php`.

| Check | Behavior (one line) | Code location (planned) | Test case(s) in `scripts/test-erd.php` (planned) |
| --- | --- | --- | --- |
| E0 | `--root <dir>` runs against a fixture tree; `--write` regenerates diagrams | `check-erd.php` args | all cases |
| E1 | Every table name in the `spec/14` domain table appears exactly once in the mapping; its target exists in a module file unless `deferred-R2` | mapping | `spec table not mapped`, `mapped twice`, `target table missing`, `deferred needs requirement id` |
| E2 | Every table in the module files appears once in the migration order; every FK target appears earlier (self-reference allowed) | migration order | `table missing from order`, `fk target after table` |
| E3 | Convention lint per column: `*_at` timestamptz · `*_on` date · `*_minor` bigint with a `currency` column in the table · `*_bps` integer · `*_id` uuid with a reference · no float/decimal · `id` uuid PK (package/framework tables exempt) · `time` needs `ref_timezone`/`timezone` · `status`/`kind`/`type` list their values or `TBD(WP-x.y)` | lint | one case per rule |
| E4 | Append-only: every table in the conventions list is marked append-only and has no `updated_at`; every table marked append-only is in the list | lint | `append-only not marked`, `append-only has updated_at`, `marked but not listed` |
| E5 | `r1-coverage.md` has each R1 ID of `traceability.md` exactly once; `Y` rows cite existing `table.column`; `N` rows have a reason | coverage | `r1 id missing`, `unknown column`, `n without reason` |
| E6 | Every column tagged `PII` is in `pii-registry.md` and every registry row names an existing column; actions come from a fixed list | registry | `pii not registered`, `registry column missing`, `unknown action` |
| E7 | The Mermaid block between `<!-- erd:diagram:start -->` and `<!-- erd:diagram:end -->` equals the one generated from the tables (`--write` fixes it) | diagrams | `diagram stale`, `write regenerates` |

## 3. Data

### 3.1 Files and format
```
docs/02-architecture/erd/
  README.md         format rules · module index · spec/14 mapping · migration order
  platform.md identity.md families.md curriculum.md scheduling.md live.md
  ledger.md billing.md learning.md messaging.md teachers.md
  pii-registry.md   design of config/privacy.php
  r1-coverage.md    R1 ID → columns
```
Each module file: a short intro, the generated diagram, then one section per table:

```markdown
### `credit_lots`
- Kind: derived · Spec: NEW (D-05) · Reqs: ATT-07, BIL-07 · Scope: student_id → family
| Column | Type | Null | References | Notes |
| --- | --- | --- | --- | --- |
| id | uuid | no | | PK (v7) |
| student_id | uuid | no | students.id | |
| amount_paid_minor | bigint | no | | D-28 |
| currency | char(3) | no | | ISO 4217 |
| expires_at | timestamptz | no | | extended by freezes |
Constraints and indexes:
- `UNIQUE (payment_allocation_id)`
- `INDEX (student_id, pool, expires_at)`
```
Kinds: `mutable` · `append-only` · `derived` (rebuildable from other tables) · `package` (schema owned by a Composer package, uuid morph keys) · `framework` (Laravel infrastructure). Mermaid shows PK/FK columns and relations, generated from the tables so it cannot drift; cross-module targets appear as attribute-less stubs.

### 3.3 Modeling choices that answer the readers' gaps
Each is a storage consequence of stated text, not a new business rule. Each appears in the module file with its source.
- **VPC gate (D-13, ADR-009 §3):** a `students` row is created only by the guardian after a granted `child_data` consent; operations never create children (ONB-12 invites the guardian). WP-1.5 tests it.
- **Students are not users** (S:4, glossary "حساب مُدار"). Child mode authenticates a `Student` through `student_pins` / `student_login_codes` on an authorized device and gets a short Sanctum token (`personal_access_tokens` polymorphic). Students can still receive in-app notifications (Laravel `notifiable` morph).
- **Child fields are exactly PRV-04 + ONB-03**: `students.first_name`, `birth_month`, `birth_year`; `student_profiles.primary_language`, `arabic_level_estimate`, self-assessment answers, `notes` (ONB-04 free text). No photo, email or address column anywhere for a child. `students.departed_at` anchors the "after the student leaves" retention clocks (F17:45-46); when it is set is decided in WP-5.2.
- **Time:** user display zone `users.timezone` (IANA) and `users.locale`; family market `families.country_code` (ONB-01 country, D-17, BIL-12 refund market). Teacher availability: weekday + local time + `ref_timezone` (`Asia/Amman`). Student availability: see D-37.
- **Audit:** `audit_logs` (append-only) holds actor id, action, entity, non-personal before/after values and `occurred_at`. IP, user agent and before/after values of registry columns go to `audit_log_personal_data` (1:1, erasable by `sura_retention`). This keeps SEC-11 (values and address are recorded) and D-14 (audit keeps the actor id only once personal data is erased).
- **Append-only tables that hold personal data** (`consents.ip/user_agent`, `participant_events`, `delivery_logs`, `session_chat_messages`, `cookie_consents`, `audit_log_personal_data`) reject UPDATE always and allow DELETE only for `sura_retention` (trigger `forbid_mutation_except_retention`, data-model-conventions.md; `safeguarding_incident_actions` too, after 7 years); the ledger, wallet, subscription events, lot extensions and version tables reject DELETE for every role. A deletion request does not shorten a legal-evidence period (consents: D-15). Recipients in `delivery_logs` are stored masked (SEC-12), with `recipient_id` for lookups. Append-only tables carry `reason_code`; free text lives in the erasable `record_notes` (privacy review), except tables whose whole row is purged by `sura_retention` or kept under D-15 (`session_chat_messages.body`, `safeguarding_incident_actions.action_taken`).
- **Sessions:** status per state-machines.md (`scheduled`, `in_progress`, `completed`, `cancelled`, `postponed`) plus `outcome`; a postponement or compensation creates a new row with `replaces_session_id`. `class_sessions.lesson_id` records curriculum progress (TCH-06); `teacher_notes` holds CLS-11 notes (registry: free text). `actual_started_at` serves the 5-minute late alert (05:31).
- **Ledger unique key:** constitution Art. 5 §2 says the unique key `(student_id, session_id, type)` applies to "قيود الحصص". Index: `UNIQUE (student_id, session_id, type) WHERE type IN ('CONSUMPTION_ATTENDANCE','ABSENCE_UNEXCUSED','EXTENSION_ABSENCE_EXCUSED','COMPENSATION_ACADEMY')`, plus `UNIQUE (reverses_entry_id)` (an entry is reversed at most once) and `UNIQUE (idempotency_key)` with deterministic key formats. A REVERSAL carries the original's `session_id` but is outside the key. A post-lock edit that must reinstate an entry already reversed (A→B→A) posts a REVERSAL of that reversal (changed after the ledger-auditor review: the earlier `ADJUSTMENT_MANUAL` path escaped every uniqueness guard). Entries post once, at attendance lock; `session_attendance.ledger_entry_id` points to the tip of the current chain and changes under a row lock. Reversing an entry whose returned credit expired at once first reverses that expiry; a replacement entry reuses the reversed entry's lot only for the quantity the reversal freed (extra charge goes FIFO to open lots, or shrinks an expired lot's expiry entry), and instant expiry is judged on the lot's net remaining after the transaction. Manual −N adjustments split across lots FIFO, one entry per lot. Recorded in ADR-007 §6 as the WP-0.7 reading.
- **Invoices:** `invoices.number` unique and sequential (BIL-11); the series format is WP-2.4's. Issuer and customer details are frozen in `issuer_snapshot` / `customer_snapshot` jsonb (allowed: snapshots).
- **Webhooks:** payment and video provider events land in `webhook_calls` (Platform, spatie), unique per provider event id, then feed `payments` / `participant_events`.
- **Enumerations the spec does not give** (lead stages, safeguarding incident status, support thread status, …) are written `TBD(WP-x.y)` with the WP that builds the feature, never invented; mechanical lifecycles (request → approved/rejected) are proposed and marked "proposed".
- **Money in settings:** the spec keys `teacher.*_jod` keep their names; their values are stored as `{amount_minor, currency}` (35 JOD = 35000 fils), never as decimals.

### 3.4 Personal-data registry (design of `config/privacy.php`)
`pii-registry.md` lists every registered column: `table.column` · subject · **Locate by** (the `table.column` path to the subject's id, or the retention clock for rows not linkable to a person) · erasure action (`erase`, `pseudonymize`, `delete_row`, `delete_file`, `retain_until_period`) · retention (F17 table, D-15, or "proposed") · source. The single config shape for WP-1.5 is the one in `pii-registry.md` (`erasure` → table → locate + columns; `retention` → table → clock + period; `honour_legal_holds`). The checker enforces tags, locate paths and that every free-text column is tagged or justified with `no-PII:`.

### 3.5 Migration order
Layered by dependency, then topologically inside each layer (the checker proves every FK target comes first): Platform core (settings, versions, files, audit, outbox) → Identity (users, package tables) → Families → Teachers core (`teachers`, `teacher_levels`, needed by RBAC scope and scheduling before WP-2.6) → Curriculum → Scheduling → Live → Billing core (plans … subscriptions, payments) → Ledger → Billing wallet (`wallet_entries`, which references the ledger) → Learning → Messaging → remaining Teachers (compensation). The three default Laravel migrations (`users` with a bigint id, `cache`, `jobs`) are replaced in WP-1.1 by uuid-based versions; that WP owns the change.

None.

## 5. Domain logic
Tooling only.
- `scripts/check-erd.php [--root <dir>] [--write]`: checks E1–E7 against `spec/14`, `traceability.md` (R1 IDs), `data-model-conventions.md` (append-only list) and `docs/02-architecture/erd/*.md`. `--write` regenerates the Mermaid blocks. Output: one summary line (`tables: N · spec/14 mapped: M · R1 covered: 210 · pii columns: K`), then errors.
- `scripts/test-erd.php`: fixture tree in `sys_get_temp_dir()`, one mutation per case, like `test-traceability.php`.
- `scripts/verify.sh`, traceability area: gate `erd` = `php scripts/check-erd.php` when `docs/02-architecture/`, `docs/01-product/spec/14-*`, `docs/03-plan/traceability.md` or `scripts/*-erd.php` changed (always on `--all`); gate `erd:selftest` when `scripts/*-erd.php` changed. CI's `traceability` job picks both up with no `ci.yml` change.
- Later WPs (WP-1.1+) can extend the checker to compare migrations against the ERD; not here.

## 6. UI (if any)
None in the product. The owner reviews the diagrams on an Arabic artifact page (module by module: what each table holds, in plain Arabic, plus the diagram), which is also the WP's roadmap station.

## 7. Security & privacy
- No child data, no secrets, no real records. Fixtures are synthetic.
- The registry is the privacy deliverable; `privacy-reviewer` reviews it, `ledger-auditor` reviews Ledger, Billing and Teachers ERDs and the append-only list.
- Encrypted columns are marked (`teacher_bank_accounts.*`, `mfa_factors.secret`); hashed: `student_pins.pin_hash`, `student_login_codes.code_hash`.

## 8. Risks & open questions
- **D-37 (Approved 2026-10-24, option a):** ONB-13 says student availability is "stored in UTC"; a weekly window stored in UTC moves by an hour for the family at every DST change (constitution Art. 6). Recommended: store weekday + local time + the family's IANA zone, like class patterns. Blocks only the `student_availability` columns; the rest can proceed.
- **D-38 (Open):** legal hold for safeguarding evidence vs ordinary retention; `legal_holds` is modelled, policy pending.
- **D-39 (Open):** marketing-message consent (CASL); no purpose added.
- Owner approval of the diagrams at the end (acceptance criterion 1) is recorded in `status.md` «اعتمادات صاحب المشروع».
- Spec ambiguities that do not change columns (dunning day origin, 14 vs 21 DST notice days, PAY-04 amount, report sampling vs states, settings keys missing for stated numbers) are listed in notes.md with the WP that must resolve them; they are not decided here.
- Size: ≈ 110 tables in 11 files. Mitigation: generated diagrams and the checker; one module per task.
- If the owner rejects a modeling choice in §3.3 at the final review, only docs change (no migrations exist yet).
